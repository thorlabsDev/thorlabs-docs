**Guided integration.** ThorNode exposes a location-specific, Yellowstone Dragon's Mouth `geyser.Geyser/Subscribe`-compatible service. The dashboard may label it **Yellowstone DM**. Authentication uses `x-token` request metadata, but the dashboard's bare dial target is not enough to build a safe client.

## Use Yellowstone when

Use Yellowstone when your application needs a long-lived, server-filtered Solana stream and can pin an onboarding-supplied protocol contract.

Choose [ThorEdge RPC](/products/thoredge-rpc) for request-response calls. Consider [Pulse Decoded Shreds](/products/pulse) for the planned QUIC transaction stream only after ThorNode confirms that replacement service is deployed.

## Connection contract

| Item                     | Value                                                    |
| ------------------------ | -------------------------------------------------------- |
| Interface                | `geyser.Geyser/Subscribe`                                |
| Target                   | Bare location dial target copied from the dashboard      |
| Authentication           | Selected access and location token in `x-token` metadata |
| Transport and trust      | Supplied during onboarding                               |
| Proto and client version | Compatible release supplied during onboarding            |
| Supported request maps   | Confirmed for the selected endpoint during onboarding    |
| Live limits              | Concurrent streams and filters shown by the dashboard    |

## Get the integration package

Copy the target and token for one location from the dashboard. Then obtain all of the following from ThorNode onboarding or [support](mailto:support@thornode.io):

- Exact transport mode for that target
- TLS server name and trust roots, or the exact trusted private-network setup
- Pinned compatible `geyser.proto` and client release
- Exact `SubscribeRequest` maps enabled on that endpoint
- Allowed fields for each map, including whether each named filter entry must be empty or populated
- Supported commitment, keepalive, error, and limit behavior

The compatible proto defines possible request maps; it does not prove that every map or filter is enabled on a ThorNode endpoint.

## Prepare the subscription

<Steps>
  <Step title="Choose one location">
    Select an active access and enabled location. Copy the bare gRPC target and
    its location token together.
  </Step>
  <Step title="Pin the supplied contract">
    Install the compatible proto or client release and apply the exact transport
    and trust configuration supplied for that target.
  </Step>
  <Step title="Attach authentication metadata">
    Send the location token on authenticated requests with the exact metadata
    key `x-token`.
  </Step>
  <Step title="Start with one verified filter">
    Open one Subscribe stream using a map and filter shape confirmed for the
    selected endpoint. Add filters only after you receive the expected update.
  </Step>
</Steps>

<Warning>
  Never append the token to the target or a query string, and never disable
  certificate or server-identity verification to make a connection succeed.
</Warning>

An integration is working when the authenticated Subscribe stream returns an update that matches the agreed map and filter. A TCP or HTTP/2 connection alone is not the success signal.

## Dragon's Mouth compatibility

The upstream [`rpcpool/yellowstone-grpc`](https://github.com/rpcpool/yellowstone-grpc) project defines the Dragon's Mouth service and publishes its [proto](https://github.com/rpcpool/yellowstone-grpc/blob/master/yellowstone-grpc-proto/proto/geyser.proto), [Node.js client](https://github.com/rpcpool/yellowstone-grpc/tree/master/yellowstone-grpc-client-nodejs), and [examples](https://github.com/rpcpool/yellowstone-grpc/tree/master/examples).

These upstream branches can change independently. Use them as protocol references only after ThorNode supplies the compatible version and endpoint-specific contract.

## Run in production

- Use bounded processing queues so a slow consumer cannot exhaust memory.
- Reconnect with bounded exponential backoff and jitter, then recreate the subscription.
- Detect stream gaps and reconcile through RPC when correctness requires it.
- Monitor current stream and filter usage in the dashboard.
- Do not assume ordering, replay, or loss behavior beyond the supplied onboarding contract.

## Troubleshooting

| Symptom                   | Verify                                                                      | Expected result                                                   | Action                                                           |
| ------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| Unauthenticated           | Metadata key is exactly `x-token`; token and target share a location        | One narrow Subscribe request authenticates                        | Recopy both values and replace the metadata                      |
| Connection or TLS failure | Supplied transport mode, server name, trust roots, and outbound gRPC policy | The client verifies the server and opens the gRPC transport       | Restore the onboarding configuration; do not bypass verification |
| Subscription rejected     | Map, filter shape, commitment, and live limits                              | One onboarding-confirmed filter is accepted and returns an update | Reduce to one verified filter and correct non-retryable input    |
| Repeated disconnects      | Client backpressure, keepalive contract, and retry loop                     | A bounded reconnect recreates one subscription without backlog    | Bound queues and reconnect according to the supplied contract    |
