Pulse exposes two live QUIC feeds from decoded Solana shreds. The sig-first feed sends transaction signatures in low-overhead datagrams. The full-tx feed sends decoded transactions on an ordered, reliable stream. Neither feed sends raw shred bytes.

Copy the Pulse target and token from the same dashboard location. The client sends the token in its first control message after opening the QUIC connection.

## Decoded transactions over QUIC

Use Pulse when you need transaction signatures or decoded transactions before building the same result through RPC calls, and your application can receive QUIC traffic.

Use [Raw Shred Stream](/products/raw-shred-stream) when you need the original shred bytes. Use [Yellowstone gRPC](/products/yellowstone-grpc) when you need a Geyser Subscribe-compatible filtered stream.

## Quick reference

| Item           | Value                                                                                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------------- |
| Dashboard path | **Endpoints** sidebar → **Endpoints** tab → **Token & Endpoints** → **Streaming** → **Pulse**                    |
| Transport      | QUIC over UDP with TLS 1.3                                                                                       |
| ALPN           | `pulse`                                                                                                          |
| Protocol       | Pulse wire v2                                                                                                    |
| Sig-first tier | `full: false`; `(slot, sequence, signature)` over unordered QUIC datagrams                                       |
| Full-tx tier   | `full: true`; decoded transactions over an ordered, reliable QUIC stream                                         |
| Authentication | Location token in the first client control message                                                               |
| Live limits    | Concurrent streams and total accounts across filters shown in **Limits**; account-capped tiers reject a firehose |

## Open a stream

<Steps>
  <Step title="Choose a location">
    Open **Endpoints**, keep the **Endpoints** tab selected, choose the access,
    network, and location, then copy the target and token from **Pulse** in the
    **Streaming** section of **Token & Endpoints**.
  </Step>
  <Step title="Configure the connection">
    Use a Pulse wire-v2 client, configure ALPN as `pulse`, and enable QUIC
    datagrams if you use the sig-first tier.
  </Step>
  <Step title="Choose a trusted network path">
    Official Pulse clients encrypt the session but currently do not verify the
    server certificate. Run them through a trusted private network or a
    UDP-capable VPN such as WireGuard. A custom client can instead pin or verify
    the endpoint certificate.
  </Step>
  <Step title="Send the first control message">
    Immediately open a client-initiated bidirectional stream and send wire
    version `2`, your chosen tier, filters, and the location token. Official
    Pulse subscribe calls perform this handshake.
  </Step>
  <Step title="Consume the selected feed">
    Read signature datagrams or full transaction frames and move application
    work to a bounded queue outside the receive path.
  </Step>
</Steps>

The first control message has this shape:

```json
{
  "token": "<PULSE_TOKEN>",
  "account_include": ["<BASE58_ACCOUNT_OR_PROGRAM>"],
  "account_exclude": [],
  "account_required": [],
  "vote": false,
  "full": true,
  "v": 2,
  "fields": []
}
```

Set `full` to `false` for sig-first datagrams. Keep at least one `account_include` or `account_required` entry when the selected tier limits account filters.

<Warning>
  Official Pulse clients do not currently authenticate the server certificate.
  Use them only over a trusted network path, or use a custom client that pins or
  verifies the certificate. Keep the bearer token out of URLs, source code, and
  logs.
</Warning>

The subscription starts when the control stream returns `{"type":"ack","ok":true,"v":2}` and the connection begins receiving data for the selected tier.

## Run in production

- Permit outbound UDP traffic to the Pulse target.
- Keep the receive path small and use bounded downstream queues.
- Monitor consumer lag and queue depth.
- Reconnect with bounded exponential backoff and jitter.
- In sig-first mode, treat a jump in `seq` as loss or reordering. The counter restarts at `0` after reconnecting and datagrams are not retransmitted.
- Use full-tx when you need decoded transaction bodies. Reconcile through RPC after reconnecting when completeness matters.
- Reuse connections instead of opening unbounded concurrent sessions.

## Troubleshooting

| Problem               | Fix                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Handshake fails       | Check the copied target, ALPN `pulse`, outbound UDP policy, and the trusted private or VPN path.                                            |
| Authentication fails  | Recopy the target and token from the same location, send `v: 2`, and put the token in the first control message.                            |
| Close code `3`        | Reduce active streams or account keys. On an account-capped tier, include at least one account or program instead of requesting a firehose. |
| No data arrives       | Confirm whether the client selected sig-first or full-tx, then decode that tier's wire-v2 payload.                                          |
| Consumer falls behind | Move expensive work downstream, bound queue growth, and use full-tx or RPC reconciliation when sig-first loss cannot be tolerated.          |
