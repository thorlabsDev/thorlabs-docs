description: "Call provider-specific transaction routes through ThorNode without separate provider accounts or API keys."
---

Bifrost aggregates provider-specific transaction routes behind your ThorNode access. The dashboard labels this product **Private TX**. When it is enabled for your selected pass or rental, ThorNode provides the route catalog, Private TX key, and location URLs.

You do not need a separate upstream-provider account, subscription, API key, or commercial agreement.

<Note>
  Bifrost aggregation is included with eligible ThorNode access at no additional
  aggregator charge. Solana network fees, priority fees, and route-specific tips
  can still apply to the transactions you sign.
</Note>

## Direct provider routes

| Good fit                                                             | Choose another product                                            |
| -------------------------------------------------------------------- | ----------------------------------------------------------------- |
| You want to call a specific provider route through one ThorNode flow | You need automatic provider selection, fallback, or smart routing |
| You do not want to manage separate provider credentials              | You need a guarantee of privacy, MEV protection, or landing       |

## Quick reference

| Item                 | Value                                                                             |
| -------------------- | --------------------------------------------------------------------------------- |
| Dashboard path       | **Endpoints → Private TX**                                                        |
| Access               | An eligible pass or rental with at least one Bifrost location                     |
| Private TX key       | The dashboard generates one per access and reuses it in each enabled location URL |
| Route URL            | Complete URL copied from the selected location and provider operation             |
| Client configuration | The Private TX key is embedded in the copied route URL                            |
| Provider credentials | Managed by ThorNode; do not add an upstream provider API key                      |
| Route selection      | Explicit: your application chooses the provider and operation                     |
| HTTP success         | A `2xx` response reports HTTP transport success; always parse the response body   |
| Chain success        | Track a returned transaction signature with your own Solana confirmation policy   |

## Create a route

<Steps>
  <Step title="Select access and location">
    Open **Endpoints → Private TX**, select the pass or rental your application
    will use, then choose an available location.
  </Step>
  <Step title="Generate a Private TX key">
    Generate the key if the selected access does not have one. The dashboard
    reuses that key in the route URLs for the access's enabled Bifrost
    locations.
  </Step>
  <Step title="Choose a provider operation">
    Select the provider and operation you want to call. The dashboard builds the
    complete route URL with your Private TX key.
  </Step>
  <Step title="Send the route-specific request">
    Copy the complete URL and send the request body required by that operation.
    ThorNode manages the upstream provider credential.
  </Step>
  <Step title="Verify the result">
    Parse the route response. If it returns a transaction signature, check that
    signature through Solana RPC until it reaches your required commitment or
    expires.
  </Step>
</Steps>

## Understand the route catalog

The dashboard lists the providers and operations available for the selected access and location. Routes can include `submit`, `batch`, `bundle`, `status`, `nonce`, and provider-specific delivery operations.

| Operation family | Typical input                           | Typical result                                |
| ---------------- | --------------------------------------- | --------------------------------------------- |
| `submit`         | One signed, encoded transaction         | A signature or provider acceptance identifier |
| `batch`          | Multiple signed transactions            | Per-item or aggregate acceptance results      |
| `bundle`         | An ordered group of signed transactions | A bundle or provider acceptance identifier    |
| `status`         | A submission identifier                 | The provider's current submission state       |
| `nonce`          | Route-specific nonce parameters         | A nonce and related metadata                  |

Request formats are route-specific. A payload for one provider or operation is not automatically valid for another, even when both routes are labeled **Submit**.

## Send a LunarLander transaction

This example uses the **LunarLander → Submit** URL copied from the dashboard. It does not require a LunarLander account or API key.

```bash
export BIFROST_ROUTE_URL='<LUNARLANDER_SUBMIT_URL_COPIED_FROM_DASHBOARD>'

curl --fail-with-body --silent --show-error "$BIFROST_ROUTE_URL" \
  --header 'content-type: application/json' \
  --data '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "sendTransaction",
    "params": [
      "<BASE64_SIGNED_TRANSACTION>",
      { "encoding": "base64" }
    ]
  }'
```

A successful route can return a Solana signature:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": "<TRANSACTION_SIGNATURE>"
}
```

Use the request format for the selected route. Do not reuse the LunarLander body for another provider or operation.

<Warning>
  A copied Bifrost route URL contains your Private TX key. Keep the complete URL
  in server-side secret storage and redact it from repositories, logs, traces,
  screenshots, and support messages. Never send a signed transaction over an
  `http://` route. Stop and contact support if a route accepts a missing or
  invalid key.
</Warning>

## Interpret outcomes

| Response                             | Interpretation                                   | Next check                                     |
| ------------------------------------ | ------------------------------------------------ | ---------------------------------------------- |
| HTTP `2xx`                           | The Bifrost HTTP request completed               | Parse the response body for a result or error  |
| Route-specific acceptance identifier | The selected provider accepted the operation     | Check the provider status route when available |
| Transaction signature                | You can query the transaction through Solana RPC | Track it to the required commitment            |

Always parse the response body after `2xx`; a JSON-RPC error can be returned in a successful HTTP response. Bifrost does not automatically choose another provider or retry through a different route.

## Troubleshooting

| Problem                     | Fix                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `401` or `403`              | Generate or copy the current Private TX key and route URL; do not add a provider API key. |
| Route not found             | Refresh the catalog for the selected access and location, then copy the route again.      |
| `2xx` with no usable result | Parse the response body and handle route-specific or JSON-RPC errors.                     |
| Signature does not land     | Apply your expiry policy or rebuild and resubmit through a route you explicitly choose.   |
