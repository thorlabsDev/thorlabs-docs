**Guided integration.** Bifrost exposes provider-specific transaction operations. The dashboard labels this product **Private TX**. You select the provider and route explicitly; Bifrost does not perform smart routing or guarantee transaction privacy, MEV protection, provider acceptance, or on-chain landing.

## Choose Bifrost

| Use it when                                                             | Choose something else when                                                       |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| You need one provider-specific operation exposed through **Private TX** | You need automatic provider selection or fallback                                |
| ThorNode has supplied its exact route contract                          | You need a self-service API whose complete public contract is already documented |

## Integration contract

| Item             | Value                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| Dashboard path   | **Endpoints → Private TX**                                                                                   |
| Integration mode | Guided integration                                                                                           |
| Route selection  | Your application chooses a specific provider route                                                           |
| Catalog          | Dashboard-displayed provider operations; availability is confirmed by the route contract and server response |
| HTTP success     | A `2xx` response reports transport success only                                                              |
| Chain success    | Track a returned signature according to your application's confirmation policy                               |

## Understand the route catalog

The dashboard catalog may include `submit`, `batch`, `bundle`, `status`, and `nonce` operations. A shared label does not make request or response schemas interchangeable.

| Possible operation | The supplied route contract must define                                     |
| ------------------ | --------------------------------------------------------------------------- |
| `submit`           | Transaction encoding, required fields, and returned identifier or signature |
| `batch`            | Item limits, ordering, per-item results, and partial-failure behavior       |
| `bundle`           | Transaction ordering, provider acceptance semantics, and failure behavior   |
| `status`           | Lookup identifier, state values, terminal states, and polling guidance      |
| `nonce`            | Nonce scope, lifetime, reuse rules, and its placement in later requests     |

Choose the operation that matches your provider workflow. A `submit` payload is not a valid `batch` or `bundle` contract merely because the same provider offers both.

## Get the route contract

ThorNode onboarding or support must supply every item below for the exact provider, operation, access, and location before the integration is runnable:

| Required artifact | Exact information needed                                                       |
| ----------------- | ------------------------------------------------------------------------------ |
| Endpoint          | Complete `https://` URL                                                        |
| Authentication    | Credential type, exact placement, scope, rotation path, and enforcement status |
| HTTP request      | Method, required headers, content type, and body schema                        |
| Route behavior    | Encodings, limits, idempotency, retry, timeout, and pacing rules               |
| Response contract | Success body, provider errors, HTTP errors, identifiers, and status lifecycle  |

<Warning>
  Do not send a credential or transaction until the exact route contract
  provides an HTTPS endpoint and confirms authentication placement and
  enforcement. Treat the credential and any credential-bearing URL as secrets.
</Warning>

There is no universal Bifrost request example because methods and bodies vary by route. Store the supplied URL in server-side configuration and redact it from logs, traces, analytics, screenshots, and support messages.

## Complete the guided integration

<Steps>
  <Step title="Select the exact route">
    Open **Endpoints → Private TX**, select the intended access and location,
    then choose one displayed provider operation. Treat it as a candidate until
    the guided contract confirms the exact access and location.
  </Step>
  <Step title="Implement the supplied contract">
    Use its HTTPS URL, authentication placement, HTTP method, headers, content
    type, and body schema without translating them from another route.
  </Step>
  <Step title="Validate the response">
    Test a non-critical request and handle the documented provider errors before
    enabling production traffic.
  </Step>
  <Step title="Track chain status">
    If the route returns a transaction signature, check it through Solana RPC
    and apply your own expiry and confirmation policy.
  </Step>
</Steps>

## Interpret outcomes

| Observable outcome                   | What it means                                                | What it does not mean                          |
| ------------------------------------ | ------------------------------------------------------------ | ---------------------------------------------- |
| HTTP `2xx`                           | The Bifrost HTTP transport completed successfully            | Provider acceptance or on-chain landing        |
| Route-specific acceptance identifier | The provider returned the identifier defined by its contract | The transaction landed or reached confirmation |
| Transaction signature                | You can check the transaction through Solana RPC             | The transaction is already landed or confirmed |

Always parse the response body even after `2xx`. Use the supplied `status` route only when its contract says it applies to the returned identifier; use Solana RPC for on-chain signature status.

## Troubleshooting

| Symptom                     | Verify                                                          | Expected result                                             | Action                                                                                           |
| --------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `401` or `403`              | Authentication scheme, placement, key scope, and active access  | The selected route authenticates the request                | Replace stale configuration; do not retry unchanged credentials                                  |
| Route not found             | Exact supplied contract and current server response             | The provider operation remains supported                    | Obtain or refresh the matching contract before changing configuration                            |
| `2xx` with no usable result | Route-specific response and provider-error fields               | The body matches the supplied response contract             | Handle the provider result; do not treat HTTP status as transaction success                      |
| Signature does not land     | Signature status, transaction expiry, and route-specific status | Your tracking distinguishes accepted, landed, and confirmed | Apply the application's expiry policy or rebuild and resubmit through an explicitly chosen route |
