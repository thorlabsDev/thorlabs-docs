Use this page to decide whether an access can support a workload. The standard tiers are **Flash**, **Classic**, **Elite**, and **Prime**; ThorNode can also grant non-standard special access. The tier name is a planning input. Product controls and server responses determine availability, while **Limits** shows the published tier row resolved for the selected access.

<Note>
  Prices, locations, product responses, usage, and published limits can change.
  Read them from the authenticated flow for the exact access you will use; do
  not copy values from a screenshot, another access, or an old integration.
</Note>

## Verify an access before integration

<Steps>
  <Step title="Select the pass or rental">
    Choose the exact active access your application will use. Do not assume two
    accesses with the same tier label have identical current configuration.
  </Step>
  <Step title="Confirm product and location access">
    Open the relevant endpoint view and check its enabled controls and offered
    locations, then confirm support through the product's server response.
  </Step>
  <Step title="Read activity and published capacity">
    Open **Usage** to review current activity and **Limits** to see the
    published tier row resolved for the selected access. Legacy access can use a
    fallback row, so treat runtime responses as authoritative for enforcement.
  </Step>
  <Step title="Test the intended configuration">
    Obtain the target and credential through the product's self-service or
    guided integration path after selecting the access, network, and location,
    then run one low-impact operation.
  </Step>
</Steps>

Success means the product's server response supports the access and location, the test reaches the product's documented success signal, and the workload stays below the relevant published and runtime-enforced constraints.

## Understand the monthly and live limits

ThorEdge RPC does **not currently enforce a monthly request-count cutoff**. Requests do not stop because a monthly compatibility counter reaches a value. If an API payload contains quota-style metadata, do not treat it as an enforced cutoff unless the authenticated dashboard explicitly presents a monthly limit for the selected access.

Live constraints still apply:

| Limit                     | What it governs                                       | When it is reached                                                         |
| ------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------- |
| RPC RPS                   | JSON-RPC request throughput                           | Requests can be throttled; inspect `429` responses and retry volume.       |
| Transaction TPS           | Transaction-submission throughput                     | Submissions can be throttled; bound application concurrency and retries.   |
| WebSocket capacity        | Connections, subscriptions, or related concurrent use | New work can be rejected; reuse connections and close idle subscriptions.  |
| Yellowstone capacity      | Concurrent streams and account or filter usage        | Subscriptions can be rejected; narrow filters and close unused streams.    |
| Raw Shred Stream capacity | Active UDP receiver registrations                     | A new registration can be rejected; remove registrations no longer in use. |
| Location access           | Locations enabled for a product and access            | A location does not appear as an available choice.                         |

The dashboard can show additional product-specific constraints. [Read **Usage** and **Limits**](/dashboard/usage-and-limits) for the selected access instead of encoding a tier table into application logic. RPC rate and subscription caps apply per active location token where the published table says so.

Creating extra clients, credentials, reconnect loops, or location targets does not increase the entitlement attached to an access.

## Distinguish tier, access, and availability

- A **tier** is the named standard class: Flash, Classic, Elite, or Prime.
- An **access** is the specific active pass, rental, or special grant selected in the dashboard.
- An **entitlement** is a product, location, or capacity currently granted to that access.

Product availability is access-specific. Access to ThorEdge RPC does not imply access to Yellowstone gRPC, Pulse Decoded Shreds, Raw Shred Stream, Replay, or Bifrost Transaction Routes. Non-standard access can also differ from the standard tier that appears closest to it.

## Operate below the live limits

- Leave headroom for bursts and retries instead of targeting the displayed ceiling.
- Bound concurrency and use exponential backoff with jitter for retryable throttling.
- Reuse WebSocket and streaming connections where the protocol permits.
- Keep Yellowstone filters narrow and close streams that are no longer needed.
- Review **Usage** and **Limits** after releases or material traffic changes.
- Contact [ThorNode support](mailto:support@thornode.io) before a planned workload needs more capacity.

For a `429`, rejected subscription, or other capacity symptom, use the [limit troubleshooting table](/reference/troubleshooting#requests-or-subscriptions-are-rate-limited).
