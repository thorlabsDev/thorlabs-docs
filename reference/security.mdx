---
title: "Security"
description: "Protect ThorNode tokens, keys, endpoint URLs, wallets, and network access."
---

Treat every ThorNode token, access key, replay key, and credential-bearing endpoint URL as a secret. Possession can be enough to consume your access or submit traffic under your account.

## Know what must remain secret

| Product                    | Secret material                            | How the client uses it                                              |
| -------------------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| ThorEdge RPC and WebSocket | The location token and complete copied URL | The dashboard-provided URL carries or resolves to the token         |
| Yellowstone gRPC           | Location token                             | Send as `x-token` request metadata, not in the target URL           |
| Pulse Decoded Shreds       | Location token                             | Send only after server identity and token enforcement are confirmed |
| Bifrost Transaction Routes | Access key and complete copied route URL   | Use only after deployment auth enforcement is explicitly confirmed  |
| Replay                     | Per-access replay key                      | Use only through the supported replay flow                          |

Wallet private keys and seed phrases are never ThorNode support credentials. Never share them with ThorNode or any third party claiming to troubleshoot your access.

## Store secrets outside code

Inject production secrets through your deployment platform or a secret manager. Use placeholders in committed configuration:

```dotenv
THORNODE_RPC_URL=<complete-url-copied-from-dashboard>
THORNODE_YELLOWSTONE_TARGET=<target-copied-from-dashboard>
THORNODE_YELLOWSTONE_TOKEN=<location-token>
BIFROST_ROUTE_URL=<complete-route-url-copied-from-dashboard>
SHREDREPLAY_KEY=<replay-key>
```

Commit an `.env.example` containing placeholders if developers need a template. Exclude the real `.env` file, secret-manager exports, wallet files, and generated configuration from version control.

<Warning>
  Deleting a committed secret in a later commit does not remove it from Git
  history. Rotate the credential first, then follow your repository provider's
  history-remediation process.
</Warning>

## Keep credential-bearing URLs private

ThorEdge RPC and Bifrost intentionally provide complete URLs that include authentication material. Use those URLs exactly as copied, but handle the **entire URL** as a secret.

Do not expose it in:

- Browser or mobile application bundles
- Git repositories, issue trackers, or CI output
- Application logs, traces, analytics, or crash reports
- Screenshots, screen recordings, or support messages
- Shell history, process supervisors, or command output visible to other users
- Referrer headers generated by opening it in a browser

Redact the credential path as well as query parameters. Keeping only the hostname, product, and location is usually sufficient for a support report.

## Use transport and network controls

- Prefer the dashboard-provided `https://` and `wss://` endpoints. A bare gRPC target does not disclose TLS; do not send a token until ThorNode supplies a TLS-verified target or an explicitly trusted private path and its trust configuration.
- For Pulse Decoded Shreds, use only a client and trust configuration that verifies server identity. Never bypass hostname or certificate verification to make a stream connect.
- For Bifrost, confirm the selected deployment enforces key authentication before use. A key-shaped URL path is not evidence that authentication is active.
- Do not replace a public hostname with a raw IP; doing so can break certificate validation and routing.
- Restrict an RPC token to a stable public egress IP when the dashboard offers that option.
- Apply host firewall and cloud security-group rules to Raw Shred Stream and Replay receivers.
- Keep internal services and local proxies off the public internet unless you add explicit authentication and network controls.

An IP restriction reduces exposure but does not make a leaked token safe. Continue to store and redact the token as a secret.

## Rotate or revoke credentials

Regenerate a location token when it may have been exposed or when the consuming system changes ownership. Regeneration or revocation invalidates future authentication with the old token for that location; other location tokens are unaffected. A streaming connection that authenticated earlier may remain open until it disconnects or the service closes it, so restart long-lived clients during rotation.

<Steps>
  <Step title="Prepare the client">
    Confirm which access, product, network, and location the client uses. Plan
    for an immediate configuration update because old and new values may not
    overlap.
  </Step>
  <Step title="Regenerate or revoke">
    Use the appropriate dashboard action for the affected credential.
  </Step>
  <Step title="Deploy and verify">
    Update the secret manager, restart or reload consumers safely, and verify a
    minimal authenticated operation.
  </Step>
  <Step title="Remove residual copies">
    Purge the old value from local files, CI variables, logs, support tickets,
    and caches where possible.
  </Step>
</Steps>

For Bifrost Transaction Routes and Replay, use the key-specific revoke or regeneration control shown by the dashboard. If no safe control is available, contact support before sharing any diagnostic material.

## Respond to suspected exposure

1. Revoke or regenerate the affected credential immediately.
2. Stop public logs, builds, or artifacts from distributing it further.
3. Review usage and access logs for unexpected traffic.
4. Replace the secret in every legitimate consumer.
5. Remove cached copies and remediate repository history if necessary.
6. Contact [ThorNode support](mailto:support@thornode.io) with the access identifier, product, location, and exposure window—never the secret itself.

See [Troubleshooting](/reference/troubleshooting#contact-support-safely) for a safe diagnostic checklist.
